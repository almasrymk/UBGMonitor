# دورة مفاتيح التوقيع والتفعيل الإنتاجي

## الحالة الحالية

R5-S01 وR5-S02: BLOCKED. العنوان الحالي مؤقت، والمفاتيح المستخرجة غير معتمدة إداريًا. لم يتغير trust verification أو license.json أو قواعد offline/device/product/clock rollback؛ يستمر تشغيل التراخيص الحالية. التسجيل المنفصل موثق في DEVICE_ENROLLMENT.md ولا يحل F-18 وحده.

## R5-S03 — إجراء تدوير المفاتيح

1. يحدد مسؤول المنصة المفتاح العام التالي ومفاتيح التوقيع الحالية التي يجب الحفاظ على دعمها، ويؤكد JWK العامة عبر قناة إدارية مستقلة.
2. يضم الإصدار القادم المفاتيح المعتمدة داخل البرنامج كمصدر ثقة ثابت؛ لا يضيف ملف license.json أو endpoint مفاتيح إلى المصدر.
3. يُنشر الإصدار الداعم قبل بدء توقيع المنصة بالمفتاح التالي، مع اختبار activation وrestart وoffline لترخيص حالي على staging.
4. يبدأ التوقيع بالمفتاح الجديد بعد انتشار الإصدار الداعم. لا تزال سياسة انتهاء صلاحية المفاتيح القديمة وإصدارات العملاء بحاجة قرار إداري؛ حذف مفتاح سابق مبكرًا قد يكسر بدء التشغيل offline.

هذا إجراء موثق؛ لا يدعي تنفيذ pinning أو تدوير مفتاح فعلي.

## R5-S06 — حدود الحماية

تثبيت public keys المعتمدة داخل البرنامج سيمنع تزوير الترخيص باستبدال token ومفاتيحه في ملف الحالة، لكنه لا يمنع مسؤول الجهاز من تعديل binary نفسه. تشفير الحالة أو تقييد ACL لا يُوصف بأنه بديل عن trust anchor.

## المطلوب قبل التفعيل

- اعتماد تسجيل إداري يدوي لكل تثبيت أو تحديد تجربة pairing بديلة؛ النسخة الحالية لا تشمل anonymous auto enrollment.
- توفير دومين HTTPS دائم معتمد وJWK عامة موثقة بصورة مستقلة، بما فيها مفاتيح التراخيص الحالية.
- مراجعة migration وتجربتها على نسخة SQL Server staging بعد backup؛ لا ينفذ Codex ترحيلًا إنتاجيًا.
- إكمال حماية اعتماد الخدمة/صلاحيات الملفات/الإدارة المحلية قبل حفظه أو إضافته للواجهة.
- تأكيد إلغاء السر المشترك الذي سبق كشفه ومراجعة استخدامه، مع خطة انتقال للاعتمادات الحالية قبل أي إلغاء قد يؤثر على العملاء.
- الموافقة على الدمج والنشر وتفعيل DeviceEnrollment:Enabled بعد التجربة؛ كل ذلك لم يحدث في هذه الجولة.
